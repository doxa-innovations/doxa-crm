# Deploying Doxa CRM on Dokploy

Deploys both apps as Dokploy **Applications** — not a Docker Compose stack. `Backend/docker-compose.yml` remains for local development only.

## Substitute before you start

Replace these placeholders everywhere they appear below:

| Placeholder | Meaning |
|---|---|
| `crm.example.com` | Public frontend domain |
| `api.example.com` | Public API domain |
| `<db-password>` | Postgres password generated by Dokploy |
| `<secret-key>` | 32+ char random string, shared by backend and frontend |
| `<webhook-secret>` | 32+ char random string |
| `<meili-key>` | 32+ char random string |

Generate secrets with `openssl rand -hex 32`.

## Topology

One project, seven services.

| Service | Type | Domain | Notes |
|---|---|---|---|
| `crm-postgres` | One-click Postgres | — | Internal only |
| `crm-redis` | One-click Redis | — | Internal only; shared by Celery and rate limiting |
| `crm-meilisearch` | Application → image `getmeili/meilisearch:v1.12` | — | Volume mounted at `/meili_data` |
| `crm-api` | Application → Dockerfile | `api.example.com` | **Replicas: 1** |
| `crm-worker` | Application → Dockerfile | — | Same image, `PROCESS_ROLE=worker` |
| `crm-beat` | Application → Dockerfile | — | Same image, `PROCESS_ROLE=beat` |
| `crm-frontend` | Application → Dockerfile | `crm.example.com` | Requires build args |

Services address each other by service name over `dokploy-network`. Traefik terminates TLS on the two public domains.

## Build settings

The three backend Applications are identical builds that differ only by `PROCESS_ROLE`:

- **Build Type:** Dockerfile
- **Dockerfile Path:** `Backend/Dockerfile`
- **Docker Context Path:** `Backend`

Frontend:

- **Build Type:** Dockerfile
- **Dockerfile Path:** `Frontend/Dockerfile`
- **Docker Context Path:** `Frontend`

The frontend build needs no outbound network beyond the npm registry: Inter is
vendored at `Frontend/app/fonts/inter-latin.woff2` and loaded via `next/font/local`,
so a network-restricted builder still succeeds.

`Kind` is where the value must be set in Dokploy. **Build arg** means the *Build Time Arguments* field, not *Environment*; Dokploy does not expose runtime environment variables during a Dockerfile build, and Next.js inlines `NEXT_PUBLIC_*` at build time.

### DATABASE_URL differs by app

The two apps use different drivers against the same database:

```env
# Backend (asyncpg)
DATABASE_URL=postgresql+asyncpg://postgres:<db-password>@crm-postgres:5432/postgres

# Frontend (node-postgres)
DATABASE_URL=postgresql://postgres:<db-password>@crm-postgres:5432/postgres
```

### Never make these build args

`BETTER_AUTH_SECRET`, `DATABASE_URL`, `SECRET_KEY`, `WEBHOOK_SECRET`, `MEILISEARCH_API_KEY`. Build arguments persist in the final image and its build history. Use Dokploy's *Build-time Secrets* if a secret is genuinely needed during a build — none are here.

## First deploy, in order

1. Create `crm-postgres` and `crm-redis` (one-click databases). Note the generated password.
2. Create `crm-meilisearch` from the Docker image with a volume at `/meili_data`.
3. Deploy `crm-api` with `RUN_MIGRATIONS=true`. It applies migrations on boot; confirm in the deployment logs.
4. Seed the default pipeline — Schedule Jobs can `docker exec` into the running container:
   ```
   python scripts/seed_default_pipeline.py
   ```
5. Deploy `crm-worker` and `crm-beat`.
6. Deploy `crm-frontend` with the three build args set.
7. Create the admin account (below).

## Admin bootstrap

Run **once**, against the production database, with the frontend's `DATABASE_URL` and `BETTER_AUTH_SECRET` in the environment:

```bash
ADMIN_EMAIL=you@yourdomain.com \
ADMIN_PASSWORD='<a real password, 12+ chars>' \
ADMIN_FULL_NAME='Your Name' \
node scripts/create-admin.mjs
```

It creates one `super_admin`, writing both the BetterAuth rows and the CRM `users` row, and refuses to overwrite an existing account.

**Never run `seed-auth-users.mjs` in production.** It creates eight demo accounts with the password `DoxaDemo123!`, which is published in this repository's READMEs. The script refuses to run when `NODE_ENV=production`, but do not rely on that alone.

## Smoke test

```bash
curl https://api.example.com/health
```

Expect HTTP 200 and `"database": "ok"`, `"redis": "ok"`. A 503 names the failing dependency.

Then, in a browser: sign in at `https://crm.example.com`, load the dashboard, and confirm the network tab shows successful cross-origin calls to `api.example.com`. A CORS error here means `CORS_ORIGINS` does not exactly match the frontend origin — scheme and host must match, with no trailing slash.

## Known limits and follow-ups

- **`crm-api` must stay at 1 replica.** Migrations run in its entrypoint; concurrent replicas would race. Scaling requires moving migrations to a CI release phase that runs `alembic upgrade head` before triggering the deploy webhook.
- **Backups are not configured.** Dokploy supports scheduled S3 backups for its one-click databases; set them up before real data accumulates.
- **Meilisearch has no domain**, which is correct — it should not be publicly reachable. Its master key must still be a real secret, not `local-development-master-key`.
- **`ENVIRONMENT=test` bypasses production validation.** The API's fail-fast checks for CORS and placeholder secrets exempt `development` and `test`. Never set `ENVIRONMENT=test` on a deployed service.
